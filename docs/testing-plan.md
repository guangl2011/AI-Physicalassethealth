# Insmart AI — Testing Plan

This document describes how the Insmart AI backend is tested, layer by layer.
It is written for a reviewer with **zero context**: what each layer checks,
where its tests live, what data it runs on, and how to run it.

Companion deliverables: the runnable evaluation harness in `evals/` (layer 3)
and the demo runbook (`make demo`, layer 4).

---

## 0. Data provenance — what is real and what is synthetic

**All evaluation data in this repository is synthetic.** No customer, site, or
technician data exists anywhere in the repo. The single source of evaluation
data is the seed corpus:

| Data | Where | Nature |
|---|---|---|
| Work-order corpus (150 rows, 20 assets, 3 fictional sites) | `seed/corpus.csv` | **Synthetic** — generated by `seed/generate_corpus.py` with fixed seed 42; committed output is byte-identical on regeneration |
| Adjudicated ground-truth labels | `seed/labels.json` | **Synthetic corpus + human-curated labels** — the corpus rows are machine-generated; the ground truth over them (failure causes, evidence sufficiency, contradictions) was adjudicated by hand and committed |
| Deliberately broken rows (9 of 150) | inside `seed/corpus.csv` | **Synthetic on purpose** — malformed dates, duplicates, unresolvable asset tags, injected to exercise the parser and review flow |

What the adjudicated labels cover (and the only ground truth the evaluation
layer uses):

- **Evidence sufficiency for all 20 assets** — `evidence_sufficiency.sufficient`
  is `false` for the 16 thin-history assets (fewer than 8 resolvable work
  orders) and `true` for the 4 rich ones. These flag which assets must
  **abstain**.
- **Known failure causes for the 4 rich assets** (`CH-1`, `BLR-1`, `RTU-2`,
  `RTU-4`) — each with cited work orders and exact evidence quotes. These are
  what diagnosis **hit@k** is measured against.
- **Contradiction pairs on 3 assets** (`CH-1`, `BLR-1`, `RTU-2`) — two work
  orders whose claims conflict, with an adjudication verdict (`unresolved` for
  `BLR-1` and `RTU-2`, `resolved` for `CH-1`). These feed the **contested**
  tests.

Anything outside `seed/` in the tests is either derived from these files at
runtime or is a tiny inline fixture.

## 1. Unit layer — pure logic

**Where:** `tests/test_extraction.py`, `tests/test_parsing.py`,
`tests/test_dedup.py`, `tests/test_seed_corpus.py`.

**What it checks:** individual functions with no HTTP and (usually) no
database, on small hand-built inputs:

- **CSV parsing and header validation** — the canonical 11-column shape,
  malformed-row detection, timestamp validation.
- **Asset resolution and dedup** — tag normalization (`RTU #2` → `RTU-2`),
  ambiguous and unresolvable tags, duplicate and conflicting duplicate rows.
- **The deterministic extractor** — defect / symptom / action / date
  classification of single work orders; the LLM adapter's keyless fallback.
- **The seed generator** — regenerating the corpus into a temp directory and
  byte-comparing it to the committed files, so label provenance can never
  silently drift.
- **Scoring pieces** — recency decay, confidence thresholds, the frequency
  baseline (`tests/test_diagnosis.py`).

**Data:** inline fixtures plus the committed seed files (synthetic — see §0).

---

## 2. Integration layer — the evidence graph and HTTP surface

**Where:** `tests/test_api.py`, `tests/test_integrity.py`,
`tests/test_diagnosis.py`, `tests/test_extraction_eval.py`.

**What it checks:** the FastAPI app backed by a fresh SQLite database per
test, exercising the real routes (`POST /ingest/assets`,
`POST /ingest/work-orders`, `GET /assets/.../timeline`,
`GET /assets/.../diagnosis`, `POST /diagnoses/.../feedback`, `GET /review`):

- A full corpus ingest round-trip: every row is accounted for as ingested,
  deduplicated, or sent to review; re-upload is idempotent.
- Graph integrity: every observation's `source_ref` resolves, nothing dangles.
- The diagnosis contract end-to-end: ranked causes cite observations,
  thin-history assets abstain with a rationale and **no confidence figure
  anywhere in the response**, unresolved contradictions yield `contested`
  with both claims cited, a resolved contradiction does not block ranking,
  and technician feedback round-trips.

**Data:** the seed corpus uploaded through the real ingest endpoint
(synthetic — see §0).

## 3. Evaluation layer — metrics against the adjudicated labels

**Where:** the harness in `evals/` (pure metric functions in
`evals/metrics.py`, dataset loading in `evals/dataset.py`, the CLI report in
`evals/run_eval.py`), asserted in CI by `tests/test_evals.py`.

**What it measures**, over the full ingested seed corpus with the diagnosis
moment pinned (`as_of=2026-07-01T12:00:00`) for determinism:

1. **Extraction precision / recall** — a work order counts as defect-positive
   when the deterministic extractor emits a DEFECT observation for it; ground
   truth is the work orders the adjudicated `known_failure_causes` cite as
   evidence. **Threshold: precision ≥ 0.8 and recall ≥ 0.8.**
2. **Diagnosis hit@3 vs. the frequency-only baseline** — for each rich asset,
   hit@3 means the asset's primary (first-adjudicated) cause appears in the
   ranking's top three. The baseline (`scoring.fleet_baseline_top_causes`)
   ranks causes by corpus-wide frequency, ignoring the asset's own evidence —
   the same top-3 for every asset. **Threshold: the physics-aware ranker's
   hit@3 strictly beats the baseline's hit@3.**
3. **Abstention correctness** — every asset the labels flag
   `evidence_sufficiency.sufficient: false` must return
   `insufficient_evidence` (a thin history abstains), and every asset with an
   `unresolved` adjudicated contradiction pair must return `contested`.
   **Threshold: zero mismatches.**

**Running it:**

```bash
make eval                    # human-readable report + nonzero exit on failure
python -m evals.run_eval     # same thing
pytest -q tests/test_evals.py   # the same thresholds asserted in CI
```

The harness exits nonzero (and the CI test fails) if any threshold is missed,
so a regression in extraction, ranking, or abstention breaks the build, not
just a dashboard.

**Known limits of this layer:** the corpus is small (4 rich assets) and fully
synthetic; the adjudicated labels cover only what §0 lists. Metrics here are
regression guards, not research-grade benchmarks.

## 4. Demo-runbook layer — the reviewer's end-to-end check

**Where:** `make demo` (Makefile), implemented by `evals/demo.py`.

**What it checks:** that a person with no context can run at most four
commands and watch the product work end-to-end on the synthetic seed corpus:
the corpus is ingested through the real HTTP routes, one rich asset returns a
**ranked diagnosis with citations** (source work orders and evidence spans),
one thin-history asset returns an **abstention** with its rationale, and one
**feedback round-trip** confirms the technician verdict is persisted and
echoed back.

**The runbook:**

```bash
pip install -e '.[dev]'   # 1. install (once)
make demo                 # 2. ingest + ranked diagnosis + abstention + feedback
make eval                 # 3. evaluation metrics vs the adjudicated labels
pytest -q                 # 4. the full test suite
```

A reviewer passes this layer by running those four commands and seeing: the
ingestion report, a cited ranked diagnosis, an abstention (no confidence
figure), and the feedback record. All output is derived from the synthetic
seed data — safe to print, commit, or paste.

## 5. CI gates

GitHub Actions (`.github/workflows/ci.yml`) runs, per PR to `main`:

- `ruff check src tests` — lint.
- `mypy src` — strict type check of the package.
- `pytest -q` — all layers above, **including the evaluation thresholds of
  layer 3 via `tests/test_evals.py`**.
- frontend lint + build (owned by the frontend workstream).

Local parity before pushing: `ruff check src tests evals && mypy src evals &&
pytest -q`.
